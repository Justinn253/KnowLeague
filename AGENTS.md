# KnowLeague Agent Guide

## Project
- Next.js 14 App Router, React 18, TypeScript, Tailwind CSS, lucide-react, and Supabase.
- Use npm and preserve `package-lock.json`.
- Write clean, readable, maintainable code to enterprise application standards, even for small changes.

## Commands
- Install: `npm install`
- Develop: `npm run dev`
- Lint: `npm run lint`
- Type-check: `npm run typecheck`
- Standard verification: `npm run check`
- Generate Riot/CommunityDragon catalogues: `npm run data:generate`
- Production build: `npm run build`

## Verification Safety
- Do not run `npm run build` while the user's dev server is running. Both use `.next`, and concurrent use can invalidate dev chunks.
- Never run more than one `next dev` process from this workspace, even on different ports. All instances share `.next` and will corrupt each other's generated routes and assets.
- Before starting the dev server, check for an existing KnowLeague `next dev` process and reuse it instead of starting another port.
- For normal edits, use `npm run check`.
- Run a production build only when explicitly requested or after confirming the dev server is stopped.
- Do not regenerate catalogues or push Supabase migrations unless the task requires it.

## Global Conventions
- Keep changes scoped and follow existing App Router and Tailwind patterns.
- For every impactful patch, append a staff changelog entry to `lib/staff-changelog.ts` in the same change. Entries must be overly specific: use a unique patch ID, the UTC ISO 8601 time the patch was made, a concise title and summary, exact behavior/data/security/operational changes, user and staff impact, affected file paths, and verification performed. Do not log routine formatting-only edits, and never include secrets or sensitive user data.
- Every `app/api` handler must be exported through `withApiMetrics` from `lib/api-metrics.ts` using a static route template; represent dynamic segments with their Next.js `[param]` names. API telemetry must remain aggregate-only and must never store request bodies, query values, headers, tokens, IP addresses, user IDs, or raw dynamic identifiers.
- Use TypeScript types and existing `@/components/*` and `@/lib/*` aliases.
- Preserve established game behavior and visual consistency unless the request changes it.
- Use generated local catalogues during gameplay; do not fetch full Riot or CommunityDragon datasets at runtime.
- Prefer existing shared helpers before adding another implementation.
- For games with a pre-game lobby or settings area, the in-match back control should return to that lobby/settings area; only the lobby back control should return to the main game hub.
- All chat surfaces must use the shared cosmetic helpers in `lib/chat-colors.ts`. Store the sender's chat color and border on each message at send time, and render from the message snapshot so both sender and receiver see identical styling and older messages keep their original cosmetics. Apply chat color and border through the inline style helpers from that file, not Tailwind color classes.
- Whenever visible UI text displays a player or user name, style that name with the user's profile chat color customization. Prefer `getChatNameStyle` or `CHAT_COLOR_NAME_HEX` from `lib/chat-colors.ts` instead of Tailwind text color classes.
- All user-authored chat write paths must call `sanitizeChatMessage` from `lib/chat-filter.ts` after trimming/length limiting and must persist the sanitized result. This applies to Skincognito, friends chat, multiplayer/lobby chat, and any future chat areas generated by AI.
- Treat multiplayer session behavior as a cross-game contract. Apply relevant lobby, presence, reconnect, moderation, discovery, and lifecycle changes to every multiplayer game unless a game-specific rule makes the behavior inappropriate.
- Keep multiplayer create/join and waiting-lobby chrome consistent with the shared quiz lobby: header layout/status pill, settings panel placement, and hidden-by-default lobby-code strip with reveal/hide and copy controls.
- Public lobby visibility toggles should update immediately when clicked and should not be part of draft settings that require an Apply Changes action.
- Do not expose service-role keys or other server secrets to client components.
- Timer UI should follow the Category Clash pattern by default: amber/yellow timer value while normal, red text with `animate-pulse` when urgent, and a countdown tick from `playUiSound('timer-countdown')` once per displayed second during the urgent window. Use a 10-second urgent window unless an existing game rule uses a different threshold.
- Use the shared `AppSelectMenu` for configurable game settings rather than native browser selects. It is the app-wide implementation of the exact Ability Blitz/Skin Champion Difficulty/Modifiers treatment: dark rounded trigger, explicit chevron padding, amber focus/open state, bordered popup with a labeled description area, spacing between individually bordered selectable options, and the established toggle/button styling. Popup menus must not add a background/drop shadow and must expand to show their complete settings content without an internal scrollbar. Settings toggles should match the same control height and dark-card styling.

## Context Routing
- UI and game components: read `components/AGENTS.md`.
- API routes: read `app/api/AGENTS.md`.
- Domain, storage, catalogue, and Supabase helpers: read `lib/AGENTS.md`.
- Database migrations: read `supabase/AGENTS.md`.
- For cross-feature work, consult `docs/architecture.md` first.
- Do not load generated JSON catalogues unless the task directly concerns their data.

## Fragile Contracts
- Current game name is Ability Blitz; `/speed-blitz` is a compatibility redirect.
- Skincognito spans client UI, API routes, `lib/skincognito.ts`, Realtime, and migrations. Trace the full flow before changing lobby lifecycle behavior.
- Profiles, friends, and contact submissions depend on Supabase RLS and authenticated/server-client boundaries.
- Data Dragon versions and generated catalogue freshness are explicit maintenance concerns, not runtime fetch decisions.
